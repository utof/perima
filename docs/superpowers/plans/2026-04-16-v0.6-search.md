#[specta::specta]
async fn search(
    query: String,
    limit: Option<u32>,
    state: State<'_, AppState>,
) -> Result<Vec<SearchHitPayload>, String> {
    if query.trim().is_empty() {
        return Ok(vec![]);

    state.search_repo
        .search(&query, limit)
        .map(|hits| hits.into_iter().map(SearchHitPayload::from).collect())
        .map_err(|e| e.to_string())
}

## Risks

- **Contentless FTS5 + triggers**: contentless mode means `UPDATE` on
  `search_index` must be a delete+insert pair (no true UPDATE). The triggers
  implement this correctly but are verbose. If trigger maintenance becomes a
  burden, switch to content-table mode (FTS5 stores data itself) at the cost
  of storage.
- **Filename extraction in SQL**: `SUBSTR` + `INSTR(REVERSE(...))` is a
  SQLite-specific idiom. Test that it handles files without a `/` (root-level
  files) and files with multiple `/`s.
- **FTS5 query injection**: user-supplied `query` is passed directly to FTS5
  MATCH. FTS5 has its own parse errors (malformed queries) — wrap in a
  `rusqlite::Error` handler and surface as `CoreError::Db`.
- **`search_after_file_tags_update` trigger**: fires on every `UPDATE` to
  `file_tags`, including the `deleted_at` soft-delete write. This is correct
  behavior but adds one FTS5 write per detach operation.
